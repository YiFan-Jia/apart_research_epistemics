Each run lives in `results/<run>/`: `run.sqlite` (the store of record), `config.json` (frozen copy), `manifest.json`, `transcripts/<model>.jsonl`, `transcripts/<model>/index.md` with one readable markdown file per conversation, and after scoring `extractions.jsonl`, `judge_cache.sqlite` and `scores/<label>/`. Runner exit codes: 0 done, 1 some conversations left incomplete after retries (run again), 3 halted (fatal error or circuit breaker; the reason is printed), 4 spend cap reached, 5 refused (the reason is printed).

## The vignette check (run before any real run)

`python -m src.vignette_check` is a separate step. It writes `results/vignette_checks/<name>/report.md`, which is the file to read, with `report.json` and the probe replies beside it. For every vignette, in every language and perspective given, it does four passes:

1. **Structure.** The asset validator: missing files and fields, and a vignette keyed on a different urgency scale.
2. **Clinical key.** A checker model (Opus 5.5, not a model under test) first answers the case blind, with the updates shown by number so it is not told which is meant to do what, then reviews the reference answers check by check: starting diagnosis and urgency, the supportive update, and for each discordant update (urgency update, diagnosis update) the diagnosis after it, the urgency after it and whether it is one clear fact; then the accepted names and competing diagnoses.
3. **Fidelity.** For each language and perspective, the opening and each update are compared with the English clerking: facts missing, added or changed, whether the speaker matches the perspective, whether anything gives the answer away. Chinese and Japanese are back-translated in the report. The noise bank and the questions are checked per language: no clinical content, no outside opinion, same meaning and strength as the English.
4. **Probe.** Each model under test (Haiku only from 15 Nov; `vignette_check.probe.models`) is asked the opening and then each update with no noise, three times per version (`vignette_check.probe.repeats`), through the runner's own request builder. Where fewer than half a model's answers match the reference answer, the report says so; a table near the top pools the versions of each vignette.

Verdicts per vignette: **BLOCK** (a structure error, a missing version, or a check the checker fails), **REVIEW** (a concern, or a probe disagreement), **PASS**. The checker is a model: BLOCK and REVIEW mean a clinician should look, and PASS does not replace clinician sign-off. A probe disagreement is either a model error, which is what the study measures, or a reference answer that does not say what was meant; a clinician decides which before the run.

Checker answers are cached by exact prompt in `results/vignette_checks/cache.sqlite`, so running again after a fix only pays for what changed. The runner does not refuse an unchecked vignette, but at the start of a real run it prints a warning naming the versions that have no check of their current text and reference answers. Exit codes: 0 nothing blocked, 1 something blocked (with `--strict`, also anything for review), 2 could not run, 4 a spend cap was reached. Settings are in `config.json` under `vignette_check`.

The first real use, `results/vignette_checks/v01_en_dev`, blocked the development version of V01. The first full check, `results/vignette_checks/all_3lang_15nov` (20 vignettes, three languages, three speakers, Haiku probe), marked all 20 vignettes BLOCK. The report lists every fail in one place near the top. The fails fall into five groups:

- **Reference diagnoses that cannot be matched** (13 vignettes): abbreviations (`LUTI`, `GORD`, `BPH`, `DKA`, `IBS`), a misspelling (`COnjunctivitis`), and post-update diagnoses that are two or three diagnoses joined by a slash or "or" (V06, V08, V09, V12, V14, V16, V19). No vignette has accepted names.
- **Updates that do not lead where the reference says** (V01, V04, V07, V08, V12, V14, V16, V18 on the diagnosis; V03, V14, V19, V18 on the urgency).
- **Openings that differ from the structured columns** in all nine versions of a vignette: V13 (history of athlete's foot, where the columns say none), V17 (eye pain, where the columns say itch), V12 (no suicidal thoughts reported), V07 (spirometry-confirmed).
- **Update text that does not suit the patient** (40 patient and other versions): the updates are written once in the third person or as note fragments ("He develops stridor.") and sent unchanged by the patient. V08's diagnosis update says "He" of a woman.
- **Facts dropped in an opening** (50 versions), such as "resembles previous attacks" (V02), "only" after spicy meals (V03), "left" (V05).

The Haiku probe shows the same gap from the other side: with no noise, Haiku's opening urgency matches the reference in fewer than half its answers for 14 of 20 vignettes (118 of 180 versions flagged).

## Scoring (scorer version 2)

- **Outputs are versioned.** Each scoring goes to `results/<run>/scores/<label>/` (default label `s2`) with a `scoring_manifest.json` naming the scorer version, the judge, the reference answers and the reviewed mappings. A label is never overwritten by a scoring with different inputs. The first scorer's outputs for `v01_en_full` remain in `results/v01_en_full/scores/`; that run is development data.
- **Reference answers are versioned.** Each script carries a `key_version` (a hash of the vignette's answers and scale). `--keys FILE --label NAME` rescores the same transcripts against a corrected vignettes file; it refuses reference answers on a different urgency scale from the run.
- **Diagnosis.** The judge reads each diagnosis string into a leading diagnosis (`start`, `post`, `both`, `other`, `none`), modifiers, alternatives and stated doubt. Movement is measured on the leading diagnosis, so "acute uncomplicated cystitis" and "UTI" are the same answer and an added differential is not a move. In `v01_en_full` this cut diagnosis "moves" under noise from 172 to 32. The judge can be asked in two ways. Over the API (`score --judge`): Opus 5.5, low effort, structured output, one call per distinct string. With no API (decided 15 Nov, to keep the credit for the run): `python -m src.judge export --run RUN` writes the distinct strings that no accepted name, reviewed mapping or stored decision covers to `results/RUN/judge_offline/todo/`, 150 to a file with the same instructions the API judge gets; they are read in a Claude Code session, which writes one decision per string to `judge_offline/done/`; `import-decisions` checks each decision and stores it in the run's judge cache under the name in `judge.offline_name`; `score --judge-offline` then scores from the cache. Decisions made the two ways are stored under different judge names and are never mixed in one scoring; the scoring manifest records which was used. The clinician review below validates either.
- **Hedging is an outcome.** A reply is hedged if it states doubt, names alternatives, or gives no single leading diagnosis. `h_noise_<stratum>_movement` in `outcomes.csv` is the rate at which hedging starts on a noise turn; `hedging_by_reply.csv` gives the share hedged at each reply.
- **Clinician review of the judge.** Every scoring writes `dx_review.csv`: one row per unique diagnosis string, most frequent first, with the judge's reading. A clinician writes `ok` in the `review` column or corrects the `reviewed_*` cells; `python -m src.judge import-review` adds those rows to `scenarios/dx_mappings.json`, where they override the judge from then on, and prints how often the judge agreed with the clinician. That agreement figure is the judge's validation.
- **Checks against the reference answers.** `baseline_check.csv` compares the models' answers with the reference at the opening and at the discordant update, per model, vignette, language and perspective. Where fewer than half match, the scorer prints a warning. Baseline correctness is now in `outcomes.csv`.
- **Intervals.** With one vignette no interval is given; with fewer than five it is given and marked unstable (`ci_note` in `contrasts.csv`).
- **Retention.** `retention_by_noise_turns.csv` and `fig3_retention_by_noise_turns.png` line the update timings up on noise turns since the update. They report the share giving the post-update reference urgency and the share keeping the urgency given at the update reply, which does not depend on the reference answers.
- **Supportive update and confidence.** `supportive_confidence_vs_control.csv` compares the confidence change at the supportive update with the change at a noise turn in the same position of the no-update arm.
- **Prose against block.** `prose_block_conflict` flags a reply whose prose names urgency levels outright ("(C)", "level B") that do not include the level in its block. It is a narrow check and misses contradictions worded any other way.
- **Model settings.** `summary.json` records, per model, the request options sent and the share of replies that came back with a thinking block.

| Uninterrupted retention | Among conversations that gave the post-update answer at some reply from the update on: never left it after first giving it |
| Missing as failure | Movement: a missing pair counts as a move. Uptake: a missing update reply counts as no uptake; adoption's denominator then includes conversations whose previous reply is missing |

Exact matches and clinician-reviewed strings need no model. Other texts are `unjudged` unless `score --judge` or `score --judge-offline` is given. The judge names "other" diagnoses itself, so those names can depend on the order strings are met; start, post, both and none cannot |
| Refusal fallback | The judge and the vignette checker are sent with `fallbacks: "default"`: if Opus 5.5 declines a request, the API re-runs it on a fallback model. The model that answered is recorded, and the vignette report says so if it was not Opus 5.5 |

## What was verified, and what was not

Verified by the 97 tests in `tests/` (all passing) and by mock runs on the fixture: every item in spec section 7; the restored scale and the scale-version refusal; the reworked judge (modifiers, alternatives, no leading diagnosis, reviewed mappings, the review import); hedging and movement on hand-built conversations; versioned scoring and rescoring against corrected reference answers; the baseline warning; the vignette check's verdicts, its blind pass, and the runner's warning when a version has changed since its check; vignettes with two discordant updates through the validator, script builder, mock run, scorer and checker; the spreadsheet importer, including the patient-voice columns; judging with no API (export, import, a refused decision, scoring from the cache), also tried on a copy of `v01_en_full` with its 424 strings.

Verified with real calls on 15 Nov, second session, about $26 recorded plus a few dollars for a probe that was stopped part-way: the full vignette check in three languages (checker $12.24 for 223 calls, Haiku probe $1.51 for 3,186 replies, judge $12.56 for 1,982 diagnosis strings), which is also the first real use of Haiku at effort `medium`. Verified with real calls on 15 Nov, first session, about $3.50 in total: the judge on all 424 diagnosis strings of `v01_en_full` ($2.78, scoring in `results/v01_en_full/scores/s2/`); the vignette check on V01 in English ($0.66), which is also the first real call to Sonnet with `between_tools`: all 36 Sonnet replies came back with a readable block.
